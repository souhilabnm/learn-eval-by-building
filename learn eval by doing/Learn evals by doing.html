Learn evals by doing them

Learn evals, observability, RAG and iteration by working on a real chatbot.

What you practise here

This page is for learning evals by doing them on a chatbot about a topic you choose. Building the chatbot is not the lesson: any simple bot that saves its answers is enough.

Evals

Read real answers and name the failures against your definition of good, then fix them and check the fix worked. Automatic checks and an LLM judge come later: see 4. Not covered yet.

Observability

Record every run so you can see why an answer went wrong.

RAG

When the bot answers from documents, test the search apart from the writing.

Iteration

Change one thing, re-run, compare, keep it only if the numbers improve.

Left out on purpose: choosing models, comparing costs, interface design and deployment. Any reasonable model works for practice.

Start here: pick a topic

Pick something you know well
You are the judge of every answer. If you cannot tell a good answer from a bad one, you cannot evaluate it.
Pick a topic with rules
Budgets, dates, policies, diets, safety limits. Rules the bot can break give you failures worth finding.
Want to practise RAG?
Give the bot 5 to 20 documents to answer from: an HR policy, product pages, your course notes, a city guide.
Topic ideas
  • Travel planner: day-by-day plans within a budget and dates. Fails by ignoring limits and inventing facts.
  • Policy bot (HR, returns, school rules) answering from a PDF. Good for RAG: wrong section, unsupported answers.
  • Study buddy for a subject you teach or studied. Fails by being wrong with confidence or too long.
  • Support bot for a made-up shop. Fails by promising what the policy does not allow.

Then get a bot to test

Spend under an hour here. The bot only needs to answer well enough to have failures worth finding.

Rules that hold in every case

      

        
Look before you automate
Read real traces first. Metrics you invent before reading data usually measure the wrong thing.

        
One failure, one check
Each judge or code check tests a single failure mode with a pass or fail answer. Avoid 1-to-5 scores.

        
Keep a regression set
Every failure you fix becomes a permanent test case, so it cannot quietly return.

        
You own quality
The person who knows what a good answer is decides the failure categories. On your own topic, that is you.

      

    

  


  
  

    

      
Project overview

      

        
The Recipe Chatbot is a small AI agent from your AI evaluations course. A person types what they want to cook and it replies with a recipe. It is a good practice project because it is simple enough to understand fully and still fails in interesting ways.

        
Under the hood: a web page for chatting (frontend), a Python server that receives each message (FastAPI), and a library that calls the AI model (LiteLLM). The course has five homeworks that follow the nine stages of this guide.

What happens when you send one message

      
Read from top to bottom. "You" is the person using the chatbot. Each column is a part of the system. Arrows show who passes what to whom. The orange arrow is where a record is saved. The green box is where evaluation happens.

      

        
      

      
Why this matters: evals can only check what was saved. These four boxes tell you what the chatbot records today, what is missing, and what to ask engineering for.

      

        
Saved today
Every chat in your browser leaves a small record (the question and the answer). Runs from the bulk test leave one results file per run, plus one trace file per question for labeling.

        
Not saved today
Which AI model answered, which version of your instructions was used, how long it took and what it cost. If the AI provider fails, nothing is saved for that message.

        
What a full record adds
Those four extras, plus every search or tool step in agents that have them. You do not add this here. You now know to ask engineering for it.

        
Good to know
The hidden instructions (the system prompt) are read once when the app starts. That is why the app restarts when you save changes to that file.

backend/ Reuse + change

        
The chatbot itself: the server and the link to the AI model.

        
main.pyReuse as is

          
The server. Receives each message, gets the answer, saves one trace file per message in annotation/traces/, and serves the chat page.
            
Change: nothing to run it. Later, ask for the model name, prompt version, time and cost to be added to each saved record.

        
utils.pyReuse as is

          
Reads the system prompt file and the model name from .env, adds the instructions to the conversation and calls the model through LiteLLM. Nothing in it is about recipes.
            
Change: nothing.

        
system_prompt.mdReplace

          
The hidden instructions ("You are an expert chef..."). The only thing that turns a general model into a recipe bot.
            
Change: write the new bot's role, rules, format and defaults. Start from your stage 1 spec.

        
retrieval.pyReuse + change

          
BM25 search over a recipe file. Not used by the chat page yet: in stage 7 you connect it to the chat so the bot answers from your own recipes.
            
Change: point it at your documents. It expects recipe fields (name, ingredients, steps, tags), so rename them to your fields.

        
query_rewrite_agent.pyReuse + change

          
Rewords a user's question into better search words before searching. Goes with retrieval.py.
            
Change: its instructions talk about cooking methods and equipment. Rewrite them for your subject.

        
evaluation_utils.pyReuse + change

          
Scores search quality: recall@k and MRR. The method works for any search.
            
Change: it looks for a field called source_recipe_id. Rename it to your document id.

      


      

        
frontend/ Reuse + change

        
index.htmlReuse + change

          
The chat page you see in the browser, with the conversation history.
            
Change: the page title and heading ("Recipe Chatbot") and the input hint ("Ask for a recipe..."). Colors are optional.

Test questions, and the tool that sends them all at once.

The test questions, one per row.

scripts/bulk_test.pyReuse as is

          
Sends every row of a CSV to the bot and saves the answers in results/results_<time>.json, plus one trace file per question in annotation/traces/ (trace_bulk_<time>_001.json and on) for the annotation app. This copy adds the trace files; the course's original saves only the results file.

Created by the bulk test. Each run adds one file.

Where chats are recorded, and a tool to label them.

        
annotation.pyReuse as is

          
The course's labeling tool for error analysis (stage 5): one chat at a time, a box for your open-coding note and one for the axial-coding group, saved into that chat's file in traces/. Don't run it from here: use the light-theme copy in useful apps/stage-5-error-analysis/annotation-app, which reads and saves this same traces/ folder. One JSON file per chat: every browser chat you have had (trace_2026…) and one file per bulk test question (trace_bulk_…). The course's 250 sample traces (trace_2024-01-15_…) sit in annotation/course_samples_extra/, so the app shows only your own chats.
            
Change: start the new project with this folder empty. Your new chats fill it.
